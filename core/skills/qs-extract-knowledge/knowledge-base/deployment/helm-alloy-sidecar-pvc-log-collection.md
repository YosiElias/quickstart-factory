# Alloy Sidecar with Shared PVC for Log Collection

## Overview

A deployment pattern where Grafana Alloy runs as a Kubernetes Deployment (not the default DaemonSet) with a sidecar container that polls an API and writes log files to a shared PersistentVolumeClaim. Alloy reads from the same PVC to process and forward logs to Loki. An init container gates startup on the data source being ready.

## Pattern Description

In the ansible-log-analysis quickstart, Alloy collects Ansible logs that are generated by a mock AAP service. Rather than collecting container stdout (Alloy's typical DaemonSet use case), it reads static log files from disk. A sidecar container (`aap-log-collector`) continuously polls the AAP Mock API and writes job logs as `.txt` files to a shared PVC. Alloy then discovers these files via glob pattern, processes them through a multi-stage pipeline, and pushes to Loki.

## Implementation

### Alloy Controller Configuration

From `deploy/helm/ansible-log-monitor/values.yaml` (alloy section):

```yaml
alloy:
  fullnameOverride: alloy
  controller:
    type: deployment  # Changed from the default DaemonSet to Deployment
    replicas: 1

    initContainers:
      - name: wait-for-aap-mock
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command:
          - sh
          - -c
          - |
            until curl -f -s http://alm-aap-mock:8080/healthz > /dev/null 2>&1; do
              echo "Waiting for AAP Mock service..."
              sleep 5
            done
            echo "AAP Mock is healthy, waiting for logs to be loaded..."
            until [ $(curl -f -s http://alm-aap-mock:8080/api/v2/jobs/ | \
              grep -o '"count":[0-9]*' | cut -d':' -f2) -gt 0 ] 2>/dev/null; do
              echo "Waiting for sample logs to load..."
              sleep 5
            done
            sleep 10
            echo "AAP Mock is ready with logs loaded! Starting Alloy..."

    volumes:
      extra:
        - name: ansible-logs
          persistentVolumeClaim:
            claimName: ansible-logs-pvc
```

### Sidecar Log Collector Container

From `deploy/helm/ansible-log-monitor/values.yaml` (alloy.controller.extraContainers):

```yaml
    extraContainers:
      - name: alm-aap-log-collector
        image: quay.io/rh-ai-quickstart/alm-aap-log-collector:latest
        imagePullPolicy: Always
        env:
          - name: AAP_API_URL
            value: "http://alm-aap-mock:8080"
          - name: OUTPUT_DIR
            value: "/var/log/ansible_logs"
          - name: POLL_INTERVAL
            value: "300"
          - name: CLUSTER_NAME
            value: "default-cluster"
        volumeMounts:
          - name: ansible-logs
            mountPath: /var/log/ansible_logs
        resources:
          limits:
            cpu: 200m
            memory: 256Mi
```

### PVC Created via Alloy extraObjects

From `deploy/helm/ansible-log-monitor/values.yaml` (alloy.extraObjects):

```yaml
  extraObjects:
    - apiVersion: v1
      kind: PersistentVolumeClaim
      metadata:
        name: ansible-logs-pvc
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 5Gi
```

### Alloy ConfigMap with Log Processing Pipeline

The Alloy config is inlined in values.yaml under `alloy.alloy.configMap.content`. It defines a multi-stage pipeline for Ansible log processing:

```
local.file_match "ansible_logs" {
  path_targets = [{
    __address__ = "localhost",
    __path__    = "/var/log/ansible_logs/*/*.txt",
  }]
}

loki.source.file "ansible_logs" {
  targets    = local.file_match.ansible_logs.targets
  forward_to = [loki.process.ansible_pipeline.receiver]
}

loki.process "ansible_pipeline" {
  forward_to = [loki.write.loki.receiver]

  // Multiline: combine PLAY, TASK, RECAP blocks
  stage.multiline {
    firstline     = "^(PLAY\\s+\\[|TASK\\s+\\[|RUNNING HANDLER...)"
    max_wait_time = "3s"
    max_lines     = 2000
  }

  // Extract cluster_name from file path
  stage.regex {
    source     = "filename"
    expression = "/var/log/ansible_logs/(?P<cluster_name>[^/]+)/"
  }

  // Extract status with priority override chain:
  // included -> ok/changed/failed/fatal/skipping -> failed/fatal -> ignoring
  // ... (4 sequential regex stages for status extraction)
}
```

The pipeline includes 16 processing stages covering multiline aggregation, label extraction from file paths, Ansible task status parsing with priority override logic, and structured metadata promotion.

## Configuration

- **Key settings:** `controller.type: deployment` overrides the Alloy chart default of DaemonSet; `POLL_INTERVAL: 300` controls how often the sidecar polls for new logs
- **Defaults:** PVC size is 5Gi; sidecar has 256Mi memory limit
- **Dependencies:** Requires AAP Mock to be running and have loaded sample logs before Alloy starts (enforced by init container)

## Gotchas

- The init container checks not just the healthz endpoint but also verifies that the AAP Mock API returns a job count greater than 0 (`/api/v2/jobs/`), ensuring sample data is actually loaded before starting log collection.
- The Alloy config expects log files at path `/var/log/ansible_logs/<cluster_name>/*.txt`, where `cluster_name` is the directory name set by the sidecar's `CLUSTER_NAME` env var (default: `default-cluster`).
- The Alloy Deployment type means only a single replica collects logs (unlike DaemonSet which would run on every node). This is intentional since logs come from a PVC, not node-local container stdout.
